# Docker Compose >>>> Kubernetes

| **Compose limitation** | **PostureSec scenario: my reasoning** | **Kubernetes mechanism: why it helps** | **Honest caveat** |
| --- | --- | --- | --- |
| **No real self-healing** | If the PostureSec database crashes, the backend may still be running but unable to serve requests correctly. In Docker Compose, I would have to detect the failure and decide what to restart. A container being "up" does not necessarily mean the application is healthy. | Kubernetes can continuously check whether the application is actually responding through **readiness and liveness probes**. If a container becomes unhealthy, the **kubelet restarts it**, and the **ReplicaSet/Deployment replaces failed Pods** to maintain the desired replica count. | This is **not automatic recovery from every failure**. Kubernetes only reacts to failures that its health checks can detect. A database can be technically alive while being logically broken, and Kubernetes cannot automatically fix an application-level problem it cannot observe. |
| **Limited scaling** | Imagine a PostureSec launch where hundreds of users suddenly hit `/api/auth/login`. With Compose, increasing capacity largely means manually running more containers and making sure traffic reaches them. There is no native cluster-level mechanism deciding when additional backend capacity is required. | Kubernetes separates **desired workload state from the individual containers**. A Deployment maintains multiple replicas, a Service provides a stable endpoint for those replicas, and the **Horizontal Pod Autoscaler (HPA)** can increase or decrease replicas based on resource or application metrics. Pods can also be distributed across multiple nodes. | HPA does **not magically make an application scalable**. It depends on sensible CPU/memory requests and limits, appropriate metrics, and an application capable of handling concurrent traffic. Poor resource definitions or a bottleneck in the database can mean adding Pods provides little or no benefit. |
| **Single-host dependency** | If the entire Docker host running PostureSec fails, the containers on that machine disappear together. Even if the application containers are stateless, the database or its data may also become unavailable. The problem is therefore bigger than simply restarting a container. | Kubernetes can schedule workloads across **multiple nodes**, so losing one node does not necessarily remove the entire application. For stateful workloads, a **StatefulSet with PersistentVolumes/PVCs** provides a structured way to manage persistent storage and stable identities. | Kubernetes alone does **not make stateful services highly available**. A PVC may preserve data without providing database replication or automatic database failover. Real HA for PostgreSQL, for example, still requires replication, backups, failover design, and appropriate storage architecture. |
