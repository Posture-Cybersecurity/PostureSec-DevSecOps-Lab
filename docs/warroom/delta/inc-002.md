## 1. Executive Summary

On 26 September 2026, POSTURESec experienced intermittent API availability degradation associated with unrestricted resource consumption on its public `GET /api/posts` endpoint.

The investigation established that the endpoint retrieved the entire posts collection without a database result limit or pagination. Each request also executed a correlated comment-count subquery. Under controlled synthetic traffic, the application experienced a significant increase in response latency and response size.

The initial reproduction created 300 synthetic posts and generated 110 requests. All 110 requests returned successfully, but peak response latency increased from 8 ms to 4,147 ms, and the largest observed response was 12,061,283 bytes. Additional concurrent testing recorded latency of approximately 5.84 seconds.

The response status codes alone did not reveal the underlying problem. The service remained reachable while the endpoint experienced substantial performance degradation. This required investigating the request path, database query and resource-consumption characteristics rather than treating the event as a conventional application outage.

As Incident Commander, I directed the investigation through reproduction, root-cause identification, temporary containment, application-level remediation and post-remediation validation.

The response consisted of two distinct control phases:

1. **Temporary containment:** Nginx request limiting was introduced to restrict bursts against the affected endpoint while the application-level remediation was implemented.
2. **Permanent remediation:** The Express application was modified to enforce bounded collection queries, pagination, per-client rate limiting and JSON request-body limits. The comment-count database relationship was also corrected.

The permanent controls were subsequently validated against the running backend and through the public Nginx path. The temporary Nginx containment was removed, and the public endpoint continued to operate successfully.

> **Final technical outcome**
>
> - Collection responses are capped at 100 posts.
> - Pagination is supported through `page` and `limit`.
> - Excessive requests from the same client receive HTTP 429.
> - Oversized JSON request bodies are rejected with HTTP 413.
> - The comment-count query uses the correct foreign-key relationship.
> - Public API functionality was verified after removing temporary containment.

The application-level remediation is implemented and runtime-validated.

**Time:** 10:12:24 UTC

**Objective:** Identify the application behavior responsible for the observed resource consumption.

### 6.1 Verify the running services


### 6.2 Inspect the running application

**Command executed:**

```bash
docker exec warroom-local-backend sh -c '
sed -n "1,260p" /app/src/routes/posts.js
sed -n "1,220p" /app/src/index.js
'
```

The original collection route contained the following query:

```javascript
router.get('/', async (req, res) => {
  try {
    const result = await pool.query(
      `SELECT p.*,
        (SELECT COUNT(*) FROM comments c WHERE c.id = p.id) as comment_count
       FROM posts p
       ORDER BY p.created_at DESC`
    );

    res.json(result.rows);
  } catch (err) {
    console.error(err);
    res.status(500).json({ error: 'Failed to fetch posts' });
  }
});
```

### 6.3 Technical analysis

The query retrieved posts in descending creation order without a `LIMIT` clause.

There was no pagination boundary. Consequently, the endpoint could return the entire collection regardless of its size.

In addition, the query calculated a comment count for every returned post. As the collection grew, this could increase database work, result size, response serialization and network transfer.

The original route also lacked application-level per-client rate limiting.

The investigation identified four relevant control gaps:

1. No upper bound on collection retrieval.
2. No pagination mechanism.
3. No application-level request-frequency enforcement.
4. No explicit JSON request-body size limit in the application configuration.

The comment-count expression also used `c.id = p.id` instead of the post foreign key, which was corrected during remediation.

### 6.4 Root-cause determination

The primary root cause was **unrestricted resource consumption caused by unbounded retrieval of the public posts collection**.

The combination of an unlimited result set and repeated requests made the endpoint vulnerable to disproportionate resource consumption.

The evidence supports an application-level resource-control failure. It does not establish SQL injection, authentication bypass or database compromise.

## 9. Permanent Remediation — Application-Level Controls

**Time:** 11:00:57 UTC

**Objective:** Correct the underlying application weakness so that protection did not depend on temporary reverse-proxy containment.

The permanent remediation modified three application files:

| File                                   | Change                                                                                              | Security objective                                |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `backend/src/routes/posts.js`         | Bounded collection query, pagination, route-level rate limiting and corrected comment relationship  | Limit database and response resource consumption   |
| `backend/src/middleware/rateLimit.js` | New per-client rate-limiting middleware                                                              | Reject excessive repeated requests                 |
| `backend/src/index.js`                | Set Express JSON parser limit to 100 KB                                                              | Limit oversized JSON request bodies                |

### 9.1 `backend/src/routes/posts.js` — Bounded collection and pagination

**Original weakness**

The original route had no result limit:

```javascript
router.get('/', async (req, res) => {
  try {
    const result = await pool.query(
      `SELECT p.*,
        (SELECT COUNT(*) FROM comments c WHERE c.id = p.id) as comment_count
       FROM posts p
       ORDER BY p.created_at DESC`
    );

    res.json(result.rows);
  } catch (err) {
    console.error(err);
    res.status(500).json({ error: 'Failed to fetch posts' });
  }
});
```

The route returned the entire result set and did not impose a maximum collection size.

**Remediated implementation**

The route now imports and applies the dedicated rate limiter:

```javascript
const { rateLimit } = require('../middleware/rateLimit');
```

The collection route now enforces a hard maximum of 100 records:

```javascript
router.get('/', rateLimit, async (req, res) => {
  const MAX_PAGE = 100;

  const requestedLimit = Number.parseInt(req.query.limit, 10);
  const requestedPage = Number.parseInt(req.query.page, 10);

  const limit = Number.isInteger(requestedLimit) && requestedLimit > 0
    ? Math.min(requestedLimit, MAX_PAGE)
    : MAX_PAGE;

  const page = Number.isInteger(requestedPage) && requestedPage > 0
    ? requestedPage
    : 1;

  const offset = (page - 1) * limit;

  try {
    const result = await pool.query(
      `SELECT p.*,
        (SELECT COUNT(*) FROM comments c WHERE c.post_id = p.id) as comment_count
       FROM posts p
       ORDER BY p.created_at DESC
       LIMIT $1 OFFSET $2`,
      [limit, offset]
    );

    res.json(result.rows);
  } catch (err) {
    console.error(err);
    res.status(500).json({ error: 'Failed to fetch posts' });
  }
});
```

**What changed**

**A. Hard result bound**

`MAX_PAGE` is set to 100. The requested limit is clamped to this maximum.

An excessively large request, such as `?limit=10000`, cannot override the maximum.

**B. Pagination**

The endpoint now accepts `page` and `limit`. It calculates an offset from the validated page number and the effective page size.

**C. Parameterized database query**

The SQL query uses `LIMIT $1 OFFSET $2`, with the values supplied separately as query parameters.

This makes the database enforce the result bound rather than relying on response-side truncation.

**D. Application rate limiting**

The `rateLimit` middleware is applied directly to the collection route. The route therefore has application-level request-frequency enforcement even when the temporary Nginx control is removed.

**E. Corrected comment relationship**

The comment-count subquery now uses:

```sql
c.post_id = p.id
```

This matches the relationship between comments and posts.

**Security effect**

The collection endpoint no longer has an unrestricted result size. The database query itself is bounded, and excessive repeated requests are subject to application-level rate limiting.

Pagination also gives clients a controlled way to retrieve the collection in smaller responses.

### 9.2 `backend/src/middleware/rateLimit.js` — Per-client request enforcement

A new middleware file was introduced:

```text
backend/src/middleware/rateLimit.js
```

**Implementation**

```javascript
const buckets = new Map();

const WINDOW_MS = Number(process.env.API_RATE_LIMIT_WINDOW_MS || 1000);
const MAX_REQUESTS = Number(process.env.API_RATE_LIMIT_MAX || 20);

function getClientKey(req) {
  return req.ip || req.socket.remoteAddress || 'unknown';
}

function rateLimit(req, res, next) {
  const key = getClientKey(req);
  const now = Date.now();

  let bucket = buckets.get(key);

  if (!bucket || now >= bucket.resetAt) {
    bucket = {
      count: 0,
      resetAt: now + WINDOW_MS,
    };
    buckets.set(key, bucket);
  }

  bucket.count += 1;

  if (bucket.count > MAX_REQUESTS) {
    const retryAfter = Math.max(
      1,
      Math.ceil((bucket.resetAt - now) / 1000)
    );

    res.set('Retry-After', String(retryAfter));

    return res.status(429).json({
      error: 'Too many requests',
      retry_after_seconds: retryAfter,
    });
  }

  return next();
}

setInterval(() => {
  const now = Date.now();

  for (const [key, bucket] of buckets) {
    if (now >= bucket.resetAt) {
      buckets.delete(key);
    }
  }
}, WINDOW_MS).unref();

module.exports = {
  rateLimit,
};
```

**What changed**

**A. Client identification**

The middleware identifies a client using `req.ip`, falling back to the socket's remote address.

**B. Request window**

The default window is 1,000 milliseconds, or one second.

**C. Request threshold**

The default maximum is 20 requests per client per window.

Both settings can be adjusted using:

```text
API_RATE_LIMIT_WINDOW_MS
API_RATE_LIMIT_MAX
```

**D. Excessive request handling**

When a client exceeds the configured threshold, the middleware returns HTTP 429 and a `Retry-After` header.

**E. Expired counter cleanup**

Expired entries are removed periodically to prevent the map from retaining expired client buckets indefinitely.

**Security effect**

Repeated requests from the same client are constrained by an application-level control. The middleware also provides an explicit retry interval for clients that exceed the threshold.

**Architectural limitation**

This implementation uses an in-memory `Map`. Its counters are local to each Node.js process. In a multi-replica deployment, different replicas would have independent counters.

For a horizontally scaled production deployment, the limiter should be migrated to a shared store or centralized gateway so that rate enforcement is consistent across replicas.

### 9.3 `backend/src/index.js` — JSON request-body limit

**Original concern**

An application accepting large JSON request bodies without an explicit size limit can consume unnecessary memory and processing resources.

**Remediated configuration**

The Express JSON parser now uses:

```javascript
app.use(express.json({ limit: '100kb' }));
```

**What changed**

The parser enforces a 100 KB JSON body limit.

Requests exceeding that limit are rejected by the parser rather than being accepted as arbitrarily large JSON payloads.

**Security effect**

This adds an independent request-ingress control against oversized JSON bodies. It complements the collection-response limit and rate limiter; it does not replace either of them.

**Objective:** Investigate why an initial public burst did not produce the expected HTTP 429 responses.

An initial public burst test returned:


## 20. Incident Conclusion

INC-002 was a reproducible API4 resource-consumption condition arising from unbounded retrieval of the public posts collection.

The investigation progressed from service-health verification to controlled reproduction, application source inspection, temporary containment and permanent remediation.

The permanent application changes addressed the underlying resource-control weaknesses rather than relying on infrastructure-level request rejection alone.

Runtime testing demonstrated that:

- The collection endpoint returned no more than 100 posts.
- Excessive collection limits were capped.
- Repeated requests from the same client were subject to HTTP 429 enforcement.
- Oversized JSON request bodies were rejected.
- Normal public API requests continued to succeed after temporary Nginx containment was removed.
- End-to-end rate limiting remained functional through the public request path.

The measured results provide evidence that the implemented controls operate in the deployed lab environment.

The remaining operational action is to transition the war-room record through its instructor-controlled lifecycle mechanism. Until that transition is recorded, the formal incident status remains active.
